┌──────────────────────────────────────────────────────────────────────────────┐
│ 6. COMMUNICATION PROTOCOL: WebSocket (RFC 6455)                              │
├──────────────────────────────────────────────────────────────────────────────┤
│ WHY?                                                                         │
│ - Full-duplex communication (bidirectional streaming)                        │
│ - Low latency (<10ms) compared to HTTP polling                               │
│ - Persistent connection (no handshake overhead)                              │
│ - Native browser support (no plugins)                                        │
│ - Perfect for real-time control and monitoring                               │
│                                                                              │
│ WHERE USED?                                                                  │
│ - Between frontend (index.html) and backend (server.py)                      │
│ - Port 8080, endpoint /ws                                                    │
│                                                                              │
│ HOW USED?                                                                    │
│ - Frontend: Send control commands (start, stop, motor speeds)                │
│ - Backend: Send simulation data at 20Hz                                      │
│ - JSON messages for data serialization                                       │
│                                                                              │
│ PURPOSE & OBJECTIVES:                                                       │
│ - Real-time command execution on hardware                                    │
│ - Live data visualization without lag                                        │
│ - Smooth user experience                                                     │
│                                                                              │
│ ALTERNATIVES CONSIDERED:                                                    │
│ ✓ HTTP Polling                                                               │
│   ✗ High latency (100ms+ per poll)                                          │
│   ✗ Server load from continuous requests                                    │
│   ✗ Not suitable for 50Hz physics loop                                      │
│ ✓ Server-Sent Events (SSE)                                                   │
│   ✗ One-way communication only (no client→server)                           │
│ ✓ Socket.IO                                                                  │
│   ✗ WebSocket with fallback, unnecessary overhead                           │
│   ✗ Larger client library (~5KB vs WebSocket native)                        │
└──────────────────────────────────────────────────────────────────────────────┘

================================================================================
                    C) ARCHITECTURE DECISION RATIONALE
================================================================================

MONOLITHIC vs MICROSERVICES
────────────────────────────
Decision: Monolithic (for now)
Rationale:
  - Single FastAPI app serves both HTTP and WebSocket
  - Easier to deploy on research institution servers
  - No inter-process communication overhead
  - Sufficient for current scale (max 10 simultaneous users)
  - Can refactor to microservices later if needed

SYNCHRONOUS vs ASYNCHRONOUS BACKEND
─────────────────────────────────────
Decision: Asynchronous FastAPI
Rationale:
  - Multiple WebSocket clients can connect simultaneously
  - Non-blocking I/O allows 50Hz simulation without blocking connections
  - Graceful handling of slow clients

REAL-TIME DATA STREAMING APPROACH
──────────────────────────────────
Decision: 20Hz broadcast via WebSocket (not 50Hz)
Rationale:
  - 50Hz = 20ms interval (simulation physics loop)
  - 20Hz = 50ms interval (broadcast to clients)
  - Reduces network traffic by 60%
  - Human perception limit ~30Hz, so 20Hz is sufficient
  - Balances responsiveness with bandwidth efficiency
